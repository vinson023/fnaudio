# 飞牛应用中心安装测试规程

日期：2026-11-19
适用：所有要在飞牛（fnOS）上验证「装得上、装完能用」的版本

## 一句话规程

**飞牛上的安装只有一条路可作数：浏览器打开应用中心，走完安装向导，再用浏览器打开应用本身。**
SSH 解包、`cmd/main start`、只轮询「登记版本变了没有」，都不能算装好。

## 为什么定这条规矩

0.2.165 是用旧脚本宣布「装好了」的：那个脚本只做一件事 —— 上传 FPK、点「同意」、
然后轮询 `/app-center/v1/app/installed` 里的版本号。它报 `INSTALL_OK`，可实际
应用中心停在安装向导第一步，应用根本没装；等真装上以后，用户点「添加目录」又
一直转圈，加不了音乐目录。

两个缺陷叠在一起才让这件事漏过去：

1. **安装向导没走**。见下一节。脚本只点「同意」，全新安装必然卡住，而失败信息
   只有一句 `registry still reports ...`，看不出是卡在向导。
2. **装好不等于能用**。登记版本 `running` 只说明进程起来了，不说明设置页能打开、
   目录能列出来。必须再用浏览器点一次真实路径。

## 应用中心有两条分支

| 场景 | 界面 | 要走几步 |
| --- | --- | --- |
| **升级**（同包名已安装） | 「未经验证应用」安全提示 | 点「同意」→ 直接装 |
| **全新安装** | 「未经验证应用」→ 安装向导 | 点「同意」→ 「运行设置 · 服务端口（默认 53199）」→ **下一步** → 「应用设置 · 普通用户文件授权」→ **安装** |

只点「同意」在升级时能过，在全新安装时必然停在向导第一步。这是
`artifacts/0.2.164/install_fpk.js` 的缺陷，已废弃，不要再用。

## 怎么跑

```bash
NODE_PATH=tools/browser-e2e/node_modules \
  node tools/install_via_app_center.js artifacts/<版本>/fnaudio-<版本>-fnpack.fpk
```

可选环境变量：`FNAUDIO_HOST`（默认 `http://192.168.5.141:5666`）、
`FNAUDIO_USER`、`FNAUDIO_PASSWORD`、`FNAUDIO_CHROME`。
`--out <dir>` 指定证据目录，默认写到 FPK 旁边的 `install-trace/`。

脚本会：登录 → 应用中心 → 手动安装 → 上传 → 同意 → **逐步点完向导** →
轮询登记状态 → 经 CGI 代理打 `/api/health` → 落 `trace.json` 与各步截图。

## 成功判据（三条，缺一条都算没装上）

1. 应用中心登记版本 == 包版本，且 `status == "running"`
2. 浏览器经 `/cgi/ThirdParty/fnaudio/index.cgi/api/health` 拿到 **200**
3. 脚本退出码 **0**（`INSTALL_OK`）

第 2 条必须走代理路径：fnaudio 在应用中心注册为 `type: "iframe"`，
`appServiceInfo.urls.path = /cgi/ThirdParty/fnaudio/index.cgi/`。`:53199` 从 LAN
直连返回 403 是**设计如此**（R565），不代表应用没起来，别拿它当判据。

## 装完还要点一遍真实路径

安装判据只覆盖「服务在跑」。用户报的「加不了音乐目录」这类问题不在判据里，
所以每次发版还要用浏览器把改动过的界面走一遍：

1. 打开 `/cgi/ThirdParty/fnaudio/index.cgi/`
2. 设置 → 音乐目录 → 添加目录 → 「我的文件」
3. 能列出目录、能选中、能保存，才算这条链路通

`artifacts/0.2.165/probe_dirs_vs_status.js` 是这条链路的接口级探针：
同一轮里交替打 `/api/library/status` 和 `/api/library/dirs`，把「慢」和
「挂死」分开，并给出每次的毫秒数。目录列表超过 1 秒就该当成缺陷查。

## 已知的误判来源

| 现象 | 不是原因 | 真正原因 |
| --- | --- | --- |
| `:53199` 打不开、403 | 应用没起来 | iframe 应用只走 CGI 代理；403 是设计 |
| 应用中心 504 / `dirs` 一直转 | 包有问题、服务端拒绝 | 见下条：请求本身被某个挂载拖住 |
| `/api/library/dirs` 要 30 秒以上 | 目录太大、扫描慢 | 每次请求都会枚举所有挂载点；离线共享（rclone/CIFS）的 `readdir` 会阻塞几十秒 |

最后一条是 0.2.165 的真缺陷：`/vol02/1000-1-9ed159d1` 是一块 rclone 云盘，
后端离线时一次 `scandir` 要 32–142 秒，而选择器每次请求都要探它，于是整个
接口超过 nginx 的 60 秒上限、返回 504，用户看到的就是「加不了目录」。
0.2.166 起：共享按 2 秒截止时间探测、结论缓存 60 秒、离线的不进根列表，
直接点它也会立刻回「这台共享存储现在连不上」。

## 不允许的做法

- 用 SSH 把 FPK 解开、`cmd/main start` 起服务，然后宣布「装好了」——那是部署，
  不是安装测试，验证不了安装向导和 iframe 注册。
- 只看登记版本号就收工。
- 拿 `:53199` 的 403 当失败，或拿它的 200 当成功。
- 安装失败后不去看 `install-trace/trace.json` 就重试。
