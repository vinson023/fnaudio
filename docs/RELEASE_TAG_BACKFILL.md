# 发布标签的补打记录

2026-11-19 补打。台账不手抄：版本、提交、日期与 FPK 哈希都由 `artifacts/0.2.165/` 下的脚本
从 `git` 与 `artifacts/` 现读生成，改一次仓库就重生成一次。

## 为什么会有这件事

`v0.2.146` 之后标签就断了：`v0.2.147` 到 `v0.2.164` 共 18 个版本发出去却没有标签，
`v0.2.145` 也漏着。补的时候又发现更早的 `v0.2.130` 同样漏着（`v0.2.129` 本来就有）。
结果是 `git describe` 停在 0.2.146，任何一个版本都没法从标签反查源码。
R602 的待办盘点把这条记成「未处理」，R608 发 0.2.165 时又确认了一次。

## 怎么补的（以及为什么不能随便补）

标签必须指向提交，所以先回答一个问题：**历史上到底有没有提交声明过这个版本号？**
把 447 个提交的 `VERSION` 文件各读一遍，得到「版本 → 提交」的完整映射，再对每个缺失版本取
**最后一个**声明它的提交——这与 `v0.2.146` 的既有做法一致（它指向该版本最后一个产物记录提交）。

补打前逐条复核过：19 个待打标签的提交里 `VERSION` 是否真等于标签名。补打后再做一次全量校验，
现在 69 个标签**全部**满足「标签名 == 该提交内的 `VERSION`」，零错配。

## 补不了的四个

这四版有归档产物，但**没有任何提交声明过它们的版本号**——版本号只在工作区里改过，从未进入历史。
给它们打标签只能指向一个 `VERSION` 是别的值的提交，那等于在标签里写假话，所以不打。

| 版本 | 归档事实 | 为什么补不了 |
| --- | --- | --- |
| `0.2.126` | FPK `679B2D7D42B4E81A…`（5,404,326 B）；构建时基线提交 `4fdc0e58`，状态 `dirty`（tracked edits 13，untracked 0） | 无提交声明该版本号 |
| `0.2.127` | 归档里没有 `SHA256SUMS` | 无提交声明该版本号 |
| `0.2.128` | 归档里没有 `SHA256SUMS` | 无提交声明该版本号 |
| `0.2.164` | FPK `052D3844BAB4B7E5…`（5,475,940 B）；构建时基线提交 `19db5233`，状态 `dirty`（tracked edits 58，untracked 37） | 无提交声明该版本号 |

要复现这四个版本，只能拿 `artifacts/<版本>/SOURCE_MANIFEST.sha256` 的逐文件哈希去比对候选源码树，
而不是指望一个标签。`0.2.164` 的出处记录写明基线是 `19db5233` 且工作区 dirty（58 处改动未提交），
也就是说它**不是**任何一个提交的干净导出——这一点在 `artifacts/0.2.164/` 里本来就有记录，本文件只是把它讲明白。

## 这些标签的效力边界

**它们锚的是源码树，不是构建输入的逐字节证明。** 每一条标签的说明里都写了这句，原因有两层：

1. 历史 FPK 多由工作区直接构建，`SOURCE_PROVENANCE.json` 里 `git_provenance_status` 普遍是 `dirty`，
   所以当年打进包里的内容比对应提交多出一些未提交改动。
2. 补打是事后行为：`2026-11-19` 打的标签，描述的是 `2026-11-11` 到 `2026-11-17` 之间发出去的版本，
   当时并没有在发版那一刻打标签。

`v0.2.165` 不受这条限制：它指向提交 `4332de53`，且该提交里的 `src/app/ui/app.js`、
`library_capability_policy.js`、`app.css`、`fnos-theme.css` 与 FPK 内同名文件逐字节相同（已核）。

## 怎么自己验

```bash
# 标签名是否都等于提交内的 VERSION（应当没有任何输出）
for t in $(git tag -l 'v*'); do
  c=$(git rev-list -n1 "$t"); v=$(git show "$c:VERSION" | tr -d '\r\n')
  [ "$v" != "${t#v}" ] && echo "MISMATCH $t -> $v"
done

# 某个版本的标签与产物哈希
git tag -n20 v0.2.160
cat artifacts/0.2.160/SHA256SUMS
```

本文件由 `artifacts/0.2.165/gen_tag_backfill_doc.py` 生成。
